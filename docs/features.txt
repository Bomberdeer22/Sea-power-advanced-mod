==============================================================================
THE ADVANCED FEATURES
==============================================================================

There are sixteen now: the twelve original ones, automatic defensive ECM,
offensive ECM in two modes, the force datalink between two co-op players, and
the laser rangefinder. All of them live in the game's own right-click menu,
each in the section a player would look in first - not stacked into one
submenu. There is no mod window and no hotkey.

  Radars, air/surface search only, active sonar, towed array, EMCON profiles
      Where it appears: Sensors

  Radar blink, auto-ARM shutoff, defensive ECM, offensive ECM, commercial disguise
      Where it appears: Sensors (they are emission decisions)

  Force datalink to the other player's force
      Where it appears: Sensors (it is about the picture the force holds)

  Laser rangefinder (LIDAR)
      Where it appears: Sensors (it is what the ship can see without
        radiating)

  ECM cones on the map
      Where it appears: Not a menu entry - drawn over the map whenever a set
        is aimed

  Salvo deconfliction
      Where it appears: Engage (it is about who may fire, and when)

  Action stations, cold cruise, crew fatigue
      Where it appears: Rules of engagement

  Sprint and drift, turn the screen onto the threat
      Where it appears: Formation

  Helicopter ladder / square / sector
      Where it appears: Air operations

  Local control, replenish alongside
      Where it appears: Damage control (replenishment falls back to
        logistics)

  Breakaway with chaff and hard rudder
      Where it appears: Top level, one click - it is the emergency button

One rule for submenus

A hull that carries a jammer has a lot to say: on a full ECM hull the Sensors
section was carrying twenty-three entries, which is a hunt rather than a menu.
So there is exactly one rule, and it is not a count per section:

  * a named group with more than one entry becomes one submenu inside the
    section it would have gone into anyway;
  * every group of one, and every ungrouped entry, is placed exactly as
    before.

Today there are two such groups, both in Sensors: Radars and sonar (radars
on/off, air search only, surface search only, active sonar, the towed array)
and ECM (auto-ARM, defensive ECM, offensive ECM, the lock list, the channel
line, what this build exposes). A ship with no ECM gets no ECM submenu - a
group of one is not a group - and a hull without sonar gets a shorter radar
submenu, not a differently shaped menu. Nothing moves between one hull and the
next because of how many sensors it happens to carry.

Sections are found by keyword at runtime, because the game's exact menu labels
are not in the API dump. If a section is missing in your build, the entry -
and the submenu it belongs to - moves up to Orders rather than disappearing,
and capabilities.txt lists the section labels that were actually found, so the
routing can be corrected from a single log rather than a guess. menu-
report.txt records which section and submenu each entry landed in for the last
menu the mod built. This document says what each one does, which game member
it drives, and - where it matters - what it honestly cannot do.

HOW TO TEST THEM
----------------

Right-click one of your ships -> Orders. You should see Weapon hatches and the
feature entries, spread across Sensors, Engage, Rules of engagement,
Formation, Air operations, Damage control and Logistics. Each toggle states
its own state in the label ("Radar blink: on - click to stop"), and each
action reports through the game's order-feedback text as well as
seapoweradvanced.log.

Anything that goes wrong is written down. capabilities.txt in the mod folder
lists every lever the mod found in your build of the game, and ecm-report.txt
lists every ECM member and type it found.

------------------------------------------------------------------------------

1. RADAR BLINK CYCLING  -  SENSORS AND EMCON
--------------------------------------------

Switches a radar on for a few seconds, then off again, on a timer. A real ship
does this so a passive anti-radiation seeker has to track an intermittent,
moving source instead of a steady beacon.

You choose which set. The entry is a submenu:

  Air search radar
      What cycles: The air-search set only
      Why you would pick it: This is the set an anti-radiation missile homes
        on

  Surface search radar
      What cycles: The surface-search set only
      Why you would pick it: Still finds ships, far harder to home on

  Both radars
      What cycles: Both, on one timer
      Why you would pick it: Two intermittent emissions, one control

A hull with no radar is not offered the entry. Stopping puts every set back
exactly as it was found - if the radar was off before, it stays off.

  Interval
      EnableSurfaceSearchRadars(bool,bool) /
        DisableSurfaceSearchRadars(bool), state read from
        IsSurfaceSearchRadarsOn: Features/BlinkSeconds, default 6 s

  Reversible
      EnableSurfaceSearchRadars(bool,bool) /
        DisableSurfaceSearchRadars(bool), state read from
        IsSurfaceSearchRadarsOn: Yes - stopping puts each radar back exactly
        as it was found

2. AUTO-ARM SHUTOFF  -  COUNTERMEASURES
---------------------------------------

When a weapon is tracked against the ship, the radars go dark for eight
seconds, then come back. This is what an anti-radiation missile forces a ship
to do, and it costs the ship its own air picture, which is why it is off by
default and opt-in per ship.

  Sensors used
      DisableAllRadars() / EnableAllRadars(bool): _incomingWeapons,
        _dangerousMissiles, ThreateningMissile (read by reflection: you cannot
        call the get_ accessor, that is CS0571)

  Honest limit
      DisableAllRadars() / EnableAllRadars(bool): The game does not label a
        missile as anti-radiation in any readable member, so any inbound
        weapon goes dark. That is conservative on purpose.

  With defensive ECM
      DisableAllRadars() / EnableAllRadars(bool): Defensive ECM wins while
        it is jamming: a jammer cannot hold a lock with the radar dark. The
        two features do not fight each other on the same ship.

2B. AUTOMATIC DEFENSIVE ECM  -  SENSORS AND EMCON
-------------------------------------------------

Every ship that carries a jammer also defends itself and its formation with
it, without being asked twice.

Arming it is a deliberate act on a ship you command - never automatic. Nothing
in the mod arms defensive ECM on its own: the two menu entries are the only
way in, and both refuse a hull that is not this machine's to command (see the
multiplayer section, §2e). A ship that stops being yours is disarmed on the
next tick.

"Carries a jammer" is read from the ship, not assumed from its shape. A jammer
is one entry in a hull's own sensor list, so the mod asks that ship's list and
takes the answer - and the answer "none" is an answer. A Huak class, with a
radar and an RWR and no set, therefore gets no ECM entries at all in its menu
and is never armed: an earlier build fell back to "it is a surface hull, so a
jammer is fitted", which armed defensive ECM on every ship in the game, put
the air-search radar on for a set that was not there, and logged a jam that
was never transmitted. A receiver cannot jam, so an RWR or ESM entry in the
list does not count as one either.

There are three possible answers, and only the first lets the feature act:

  Fitted - an ECM set is in the ship's sensor list (or, if the list cannot be read, the game's own isOffensiveEcmSystemAvailable says yes)
      What the mod does: everything works as described below. If the list
        holds something named like ECM but the game's own availability flag
        says this hull cannot jam offensively, the answer is no - the game's
        own flag is the one its AI and weapons panel ask

  None - the sensor list was read and holds no ECM set, or the game's own flag says no
      What the mod does: no ECM entries on that hull at all, and ArmFleet
        skips it and says so

  Unreadable - neither the list nor a flag could be read
      What the mod does: the ECM entries appear, with one line saying the
        fit could not be read, but nothing is armed automatically - the
        automatic defence never acts on a maybe, and ecm-report.txt records
        exactly what could not be read

ecm-report.txt (written from ECM: what this build exposes in the menu) now
ends with a jammer fit by hull list, one line per hull class in your fleet,
saying which of the three it is and what said so. That is the file to send if
a ship with a jammer is treated as having none, or the reverse. When a vampire
- a weapon the game is tracking against this ship, or against any ship of the
task force within 25 nm - appears, the mod:

  1. puts the air-search radar on. A jammer needs a fire-control quality
     bearing to know where to point, and that bearing comes from radiating.
     This is the price, and it is not optional: while the jammer works, the
     ship is the loudest thing in the water. It is the same trade a real
     commanding officer makes, and it is why the feature is armed deliberately
     rather than always on.
  2. hands the missile itself to the jammer as its target, so the set is
     pointing at the seeker rather than at a bearing the mod computed.
  3. raises power or mode, where this build exposes a control whose units the
     mod can trust.
  4. holds the lock - the target is re-pointed four times a second for as long
     as the missile is tracked, so a lock that the game clears is immediately
     re-established.

When the sky has been clear for six seconds it stands down, stops jamming, and
puts the air-search radar back exactly as it was found.

  Sensors
      The game's own ECM switch, ECM target member and power/mode member -
        all found at runtime by name, never guessed (see
        Interop/EcmControl.cs): Air-search radar on for the duration; that is
        the deliberate cost

  Range
      The game's own ECM switch, ECM target member and power/mode member -
        all found at runtime by name, never guessed (see
        Interop/EcmControl.cs): Defends the ship and any task-force ship
        within 25 nm of it

  Honest limit
      The game's own ECM switch, ECM target member and power/mode member -
        all found at runtime by name, never guessed (see
        Interop/EcmControl.cs): The mod cannot promise the missile misses. It
        points the game's jammer at the game's missile and keeps it there;
        whether the seeker breaks lock is the simulation's answer. "Almost
        impossible to resist" is not something a mod can guarantee without
        knowing the game's jamming model, and this one does not pretend to.

  Honest limit
      The game's own ECM switch, ECM target member and power/mode member -
        all found at runtime by name, never guessed (see
        Interop/EcmControl.cs): If this build names its jammers something the
        scan does not recognise, the feature says so in the menu and writes
        ecm-report.txt listing every ECM-like member it found. That file is
        ground truth from the installed game and is the fastest way to make
        the next build exact.

Which units get which entries

The mod only offers an option to a unit that can carry it out:

  ECM (defensive, offensive, mode and lock)
      Shown for: hulls the game says carry ECM, and surface hulls where it
        does not say. Never on submarines

  Active sonar, towed array
      Shown for: hulls that report the fit, or where the game does not
        report one

  Helicopter search patterns
      Shown for: hulls with a flight deck or hangar, or surface hulls where
        the game does not say

  Replenish alongside
      Shown for: surface hulls

  Jam with ECM on a contact
      Shown for: hostile and neutral contacts, identified or not, when one
        of your ships carries a jammer. If a jammer exists in the fleet but
        none is close enough, the contact menu says so instead of silently
        adding nothing

  Sensors -> Defensive ECM: off - click to arm automatic jamming
      What it does: Arms this ship

  Sensors -> Defensive ECM: task force off - click to arm N ship(s)
      What it does: Arms every ship under command that carries a jammer

  Sensors -> Defensive ECM: on for N of M ship(s) - click to disarm the task force
      What it does: The same entry once anything is armed: stands the whole
        force down in one click

  Sensors -> ECM: what this build exposes
      What it does: Writes ecm-report.txt again on demand

2C. OFFENSIVE ECM, TWO MODES  -  SENSORS AND EMCON
--------------------------------------------------

The ship's jammer, used deliberately. There are two modes and the default is
the one that changes nothing.

Standard (default)

The game's own ECM behaviour. The mod does not touch the set, does not radiate
for it, and switches back to this the moment you pick it - which also releases
any lock it was holding. If you never open this menu, nothing about your
jamming changes.

Focused (the mode that does something)

Two ways in, and both end in the same place:

  * Right-click the enemy contact itself -> Jam with ECM. That is the only
    entry the mod adds to a contact's menu; the game's own identification
    entries (mark hostile/neutral, request identify) are untouched. The mod
    picks whichever of your ships carries a jammer is nearest and inside
    range, and names it in the label, so you do not have to work out which
    hull carries the set. The contact does not have to be identified first.
  * Right-click your own ship -> Sensors -> Offensive ECM lock and pick a
    contact from the list (the contacts the task force holds, nearest first,
    max 150 nm for ships and 150 nm for aircraft). The list is there whatever
    the mode toggle says - picking a contact is what switches the mode.

Aircraft and helicopters

Planes can be locked too, and the reach is set separately for them:

  Ship or sea-skimming missile
      Reach: JamRangeNm, 150 nm
      Note: The mod's reach: what it will offer and how far it will hold a
        lock. Whether the jam bites at that distance is the game's own ECM
        model deciding

  Aircraft or helicopter
      Reach: JamAirRangeNm, 150 nm
      Note: Also 150 nm. In the real world this is the easier of the two - a
        masthead sees 4.5 nm, an aircraft at 15,000 ft sees 65 nm on its own

Stated plainly, because it is the one place this feature overreaches the
physics: 150 nm ship-to-ship is well past the radio horizon. The mod will
point the jammer and hold the order at that range; if the game's radar
calculator decides the jam does not degrade a set that far away, that is the
simulation's answer and the menu still shows the lock. What the second half -
holding the target's own sensors down - does at range is unaffected, because
it reaches the target's own switches rather than the other radar's receiver.

Jamming an aircraft is not the same as jamming a ship, and the mod says so
rather than pretending otherwise:

  * it carries one radar, not a ship's families. Radar off means blind, and
    its crew can put it back up between assertions like anyone else's.
  * its receiver cannot be jammed off at all - a passive set has nothing to
    switch down - so the report says that instead of claiming a clean sweep.
  * the entry names the type and whether it has been identified: Jam E-2C
    Hawkeye - aircraft (68 nm) or Jam Skunk 14 - unidentified, aircraft (68
    nm).

Where the contacts come from

The picture is the player's side's, read from the two places the game actually
keeps it:

  Taskforce.PlottingTable.LocalVehicles
      What it is: the map itself: every foreign track this machine holds,
        keyed by the object behind it. A track in here may be completely
        unidentified and is still a contact

  Taskforce._spottedObjects
      What it is: what the side's sensors have reported, which can include a
        contact before the table has given it a number

Nothing is invented, and identification is never a filter: the count that is
read is "foreign contacts held", not "identified contacts". offensive-ecm.txt
records which of the two was read and how many contacts were in each state, so
"nothing was offered" can be told apart from "the mod could not see the
picture".

What the lock actually does

  0. Only from a ship that carries a jammer - the same per-hull fit as
     defensive ECM (§2b). A hull with no ECM set in its sensor list is never
     chosen as the jammer, so a contact menu will say no ship with ECM is in
     range rather than offering a jam from a ship that cannot transmit.
  1. Issues the game's own jam order - setOrder(Order.Type.Jam, target,
     displayOrderText) for a contact the picture has identified, or the
     bearing form of the same order for one it has not. This is the order the
     weapons panel issues when a player points a pod at something, so the
     game's own ECM does the work: it selects the set, records the order, and
     registers the assignment where its radar model reads it.
  2. That is the jam. The game's radar calculator now treats the target as
     jammed; the cone on the map is live, and in a session the multiplayer mod
     forwards the same order to the host.
  3. Offensive ECM: hold its sensors down too is the second, deliberate order,
     and it is the extra half: instead of only degrading what the target sees,
     the mod switches the target's own radar families, sonar and towed array
     off and keeps them off, re-asserted ten times a second. This half needs
     the contact to be identified - there is nothing to hold down on a track
     nobody has named - and it is offered only when the picture says the
     contact is identified. It is a burst, not a switch: it runs for one
     window and then the contact's crew get their sensors back for a while. A
     menu line under the lock reports N of M suppression channel(s) in use and
     names the ships using them.
  4. stop stops that second half and leaves the game's jam running; Release
     the ECM lock takes the jam down through the game's own teardown
     (ceaseOffensiveJam), which is the only thing that also removes the set
     from every victim's list.
  5. stands the lock down when the target is sunk, runs beyond range, you
     release it, or you go back to standard.

  Reads
      The game's own jam order (setOrder(Order.Type.Jam, ...), unit and
        bearing forms), and - for the second half - the target's own switches:
        DisableAllRadars(), DisableAirSearchRadars,
        DisableSurfaceSearchRadars, TowedSonarsSetActive(false),
        DisableActiveSonars, plus any ESM / jammer switch it exposes: Its
        radiator state (IsAirSearchRadarsOn, IsSurfaceSearchRadarsOn), its
        sensor fit (HasTowedSonar, HasActiveSonar), its hull signature from
        its parameter block

  Range
      The game's own jam order (setOrder(Order.Type.Jam, ...), unit and
        bearing forms), and - for the second half - the target's own switches:
        DisableAllRadars(), DisableAirSearchRadars,
        DisableSurfaceSearchRadars, TowedSonarsSetActive(false),
        DisableActiveSonars, plus any ESM / jammer switch it exposes:
        Features/JamRangeNm, default 150 nm against ships;
        Features/JamAirRangeNm, default 150 nm against aircraft. Both go to
        300

  Cost
      The game's own jam order (setOrder(Order.Type.Jam, ...), unit and
        bearing forms), and - for the second half - the target's own switches:
        DisableAllRadars(), DisableAirSearchRadars,
        DisableSurfaceSearchRadars, TowedSonarsSetActive(false),
        DisableActiveSonars, plus any ESM / jammer switch it exposes: None in
        emissions. This mode runs on EMCON: it never switches the attacking
        ship's radar on, so the jammer gives away nothing while it works. (The
        defensive feature does need air search - it is locking onto a missile,
        not a contact.)

  Result you will see
      The game's own jam order (setOrder(Order.Type.Jam, ...), unit and
        bearing forms), and - for the second half - the target's own switches:
        DisableAllRadars(), DisableAirSearchRadars,
        DisableSurfaceSearchRadars, TowedSonarsSetActive(false),
        DisableActiveSonars, plus any ESM / jammer switch it exposes: The
        game's jam, immediately, from the lock. Then, if the second half is
        ordered: every sensor off, or NOT all sensors off - <sensor> would not
        switch off on this build. The second is not a bug in the lock: it
        means the game gives no way to reach that one sensor family, so it is
        still working. The menu names it and offensive-ecm.txt lists it as
        STILL. The mod does not edit the target's picture to hide that. On an
        unidentified contact there is no second half to order, and the menu
        says so rather than offering a button that cannot do anything.

  Honest limit
      The game's own jam order (setOrder(Order.Type.Jam, ...), unit and
        bearing forms), and - for the second half - the target's own switches:
        DisableAllRadars(), DisableAirSearchRadars,
        DisableSurfaceSearchRadars, TowedSonarsSetActive(false),
        DisableActiveSonars, plus any ESM / jammer switch it exposes: The
        game's jam lasts as long as the lock is held. The second half - the
        switch-off - is a burst: it runs for a set window, then the contact's
        crew get their sensors back for a recovery period before it can be
        held down again. There is also a limit on how many contacts the task
        force can hold blind at once. See below.

Making it less powerful

The second half was the strongest thing in the mod, and it was unlimited in
the two ways a real jammer is not: it never ran out, and there was no limit on
how many contacts were kept blind at the same time. Two limits now, both
settings, both stated in the menu before the click and in offensive-ecm.txt
afterwards:

  Features/EcmJamChannels
      Default: 2
      What it means: How many contacts the task force may hold blind at
        once. This is the expensive half only: every lock still gets the
        game's own jam, so a lock with no channel free is a jam without the
        blinding, and the menu says which ships are using the channels

  Features/EcmJamHoldSeconds
      Default: 60
      What it means: How long one hold lasts. When it runs out the mod
        simply stops switching the contact's sensors off - it switches nothing
        back on for the enemy, the game's own crew does that - and the game's
        jam continues

  Features/EcmJamRecoverySeconds
      Default: 15
      What it means: After a hold ends, the same contact cannot be held down
        again for this long. Without it the window would be a formality: the
        player would re-order the instant it lapsed and the target would never
        get a sensor back

Why the channel budget is the task force's, not one ship's. A ship's jammer
already holds one contact - the game gives a set one assignment - so a per-
ship figure above one would be a promise the simulation would not keep, and
the mod does not make those. What is finite is the expensive half: a few
tracks held blind at a time, staffed and run from the force's electronic
attack cell, with everything else getting the game's own jam. A player who
sets 99 gets the 0.22.1 behaviour back; 1 makes it a single-track weapon.

The recovery window is not skippable: stopping a hold by hand, releasing the
lock, and running out of window all start it. Re-ordering during it is refused
with the seconds named. The defensive dive's guidance channels (§2f) are a
separate budget: defending a ship and blinding someone else's do not compete
for the same number.

And it checks itself. Five seconds after a hold ends the mod reads the
contact's sensors once and writes down whether anything came back up. It
cannot switch them on for the enemy - that would be radiating on someone
else's behalf - so the target's own side has to do it, and if it does not, the
window is not buying the target anything on that build. The log line is 5 s
after the hold on <target> ended: N of M sensor famil(ies) radiating - ...,
and a zero after it says the limit needs another look. Send that line with the
report.

Three settings, three presets:

  Shipped
      Channels: 2
      Hold: 60
      Recovery: 15
      What it feels like: Two tracks blind at a time; a target is off the
        air for a minute, then has a quarter of a minute with its radar back

  Single track
      Channels: 1
      Hold: 45
      Recovery: 30
      What it feels like: One contact at a time, and it gets a long look
        between windows

  0.22.1, unlimited
      Channels: 99
      Hold: 0
      Recovery: 0
      What it feels like: Every lock blinds its contact for as long as it is
        held - the version that was too strong

offensive-ecm.txt in the mod folder records every lock, appended rather than
overwritten: which kind of target it was, which contact lists the picture was
read from, the signatures read off the target, what was silenced, what was
not, and the jammer path used. It is the file to send if the target does not
go quiet when it should - and the file to send if an aircraft does not appear
in the lock list at all.

2D. THE ECM CONES ON THE MAP  -  SENSORS AND EMCON
--------------------------------------------------

A jammer is directional and a menu cannot show you which way it is pointing,
so the mod draws it:

  Offensive set, locked, game jam running
      What you see: a long, narrow cyan beam from the jammer to the contact
        it is locked on, bright - the game's own jam is live

  Offensive set with the sensors held down
      What you see: the same beam, with ECM JAMMING on the far end; that is
        the second half working

  Defensive set, engaged
      What you see: an amber beam to the missile it is tracking, with a
        marker on the missile

  A ship with ECM selected, nothing aimed
      What you see: a small cyan box on the ship and ECM ready

The beams are deliberately long and narrow - they are bearings, not areas, and
a cone wide enough to look like a search fan would be telling you something
that is not true.

  Where the ends come from
      IMGUI, like the rest of the overlay - no assets, no XAML:
        Interop/MapProjection.cs, in order: the map's own arithmetic (0.2°
        tiles at 330.71396 world units, offset by Globals._currentCenterTile)
        - exact, and the only route that works here because this build's units
        are ECS data with no Unity transform; then any GeoPosition->Vector3
        method the game exposes; then a Unity transform on the unit. The
        result is projected through the map camera

  If neither exists
      IMGUI, like the rest of the overlay - no assets, no XAML: nothing is
        drawn, one line appears at the bottom of the screen saying so, and
        ecm-cone.txt records exactly what was looked for. A cone in the wrong
        place would be worse than none

  Setting
      IMGUI, like the rest of the overlay - no assets, no XAML:
        Features/ShowEcmCone, default true

  Follows the selected unit
      IMGUI, like the rest of the overlay - no assets, no XAML: the game's
        own selection member if the mod can find one, otherwise the unit whose
        right-click menu you opened last

If the cones do not appear, ecm-cone.txt in the mod folder is the file to send
- not ecm-report.txt. It records the centre tile the map arithmetic used,
where lat/lon 0,0 lands in world space, where that projects to on a screen of
known size, which camera was chosen and what other cameras were available. A
beam in the wrong place and a beam that never appears have different causes,
and those four numbers tell them apart.

2E. USING IT WITH THE MULTIPLAYER MOD
-------------------------------------

The multiplayer mod (SeapowerMultiplayer, com.seapowermultiplayer.plugin) is
supported: the mod detects it, works out whether this machine is the host or
the client, and changes what it promises accordingly. It is reached by
reflection, so nothing changes for players who do not have it, and nothing
breaks if it is not installed.

multiplayer.txt in the mod folder says what was found and which rules followed
from it. It is rewritten when a session comes up or ends.

Every feature, and what a client gets

There is one table, in the mod itself (Interop/Multiplayer.cs), and it is the
only place these decisions are written down. Each feature is one row: how it
reaches the simulation, and therefore what happens when this machine is the
client. The menu's refusal text, the report, and the features themselves all
read that row, so they cannot contradict each other. The whole table is
printed in multiplayer.txt every time it is written - read it there rather
than trusting this page to stay in step.

Four routes, and the route is what decides everything:

  ORDER
      Meaning: the game's own order (a jam, a waypoint, a launch)
      On a client: sent; the multiplayer mod forwards it, and the host runs
        the game's own task

  CALL
      Meaning: a call on the game's own object (a sensor switch, a weapon
        status, a doctrine flag)
      On a client: sent, and the host may accept or override it. The mod
        records what was sent; the report says so

  READ
      Meaning: reads the game's state and draws it
      On a client: unchanged - it shows what this machine knows

  LOCAL
      Meaning: the mod's own write, to state the host simulates
      On a client: not attempted: the host reverts it within a frame, so the
        menu says why instead of offering a click that cannot work

Ordered by the feature you would click:

  Radars and sonar switches
      Route: CALL
      On a client: sent, and the session throttles a repeat toggle on the
        same set within ten seconds. A throttled toggle does not move locally
        either, so a label can take a moment to catch up

  Radar blink
      Route: CALL
      On a client: half-cycle raised to at least 12 seconds so the throttle
        does not eat a flip; each flip is checked four seconds later, and a
        flip the host refused stops the blink instead of pretending

  Auto-ARM shutoff
      Route: LOCAL
      On a client: not offered: the host decides when a ship radiates, and a
        cut written here is reverted

  Defensive ECM
      Route: LOCAL
      On a client: not offered: weapons are simulated by the host, so

Yours is yours: one client cannot switch another's ECM on

The fleet list on a co-op client holds every friendly ship on that side,
including the ones the other player commands. Everything in this mod that
arms, engages, jams or holds acts only on ships this machine commands, and the
answer comes from the multiplayer mod's own rules rather than from a guess:

  UnitLockManager.BlocksOrdersFor(unit) - the other player has claimed this unit, and that mod refuses every order for it
      What this mod does with it: touches nothing on it: no arming, no jam,
        no hold, no mode change. The menu says whose ship it is

  TaskforceAssignmentManager.ClientMayControl(unit) - the host assigned this client a particular task force
      What this mod does with it: the same: a ship outside the assignment is
        not this client's to task

  neither readable (an older or newer build of that mod)
      What this mod does with it: per-ship clicks still work - the player is
        clicking a ship they can see - but fleet-wide arming is refused,
        because "all my ships" cannot be told from "everybody's ships"

That closes the specific bug behind this: arm the whole task force used to arm
every friendly hull, including the other player's command. The other client
then saw its own ships' radars come on and their jammers transmit with nobody
having asked - defensive ECM appearing to switch itself on. A ship this
machine no longer commands is disarmed on the next tick and the log says why,
so an old arming cannot survive a change of hands either.

And nothing arms defensive ECM except a click: the per-ship entry, or for the
whole task force. There is no automatic arming path in the mod - the feature
only ever arms what the player pointed at. ecm-report.txt carries the audit:
how many ships are armed here, and how many of those this machine does not
command (which should be zero, and is the number to send if it ever is not).

Proving it, one path at a time

This is the least-exercised code in the mod, because only a client can prove
it, and a table of intentions is not evidence. So every one of those paths
records itself: when a feature is used, the mod writes down that it was tried,
on which unit, and whether it reported success. multiplayer.txt ends with that
list, plus a count of how many paths a client can actually take are still
untried this session. Twelve of the sixteen rows are paths a client acts on -
the three LOCAL ones are refused before anything is written and the READ one
writes nothing, so counting them as "untried" would overstate the work left. A
session that exercised three of the twelve shows nine unproven, rather than
implying that twelve work.

That is deliberate: the numbers are meant to be uncomfortable until somebody
flies a client through them. If a path reports "no effect" in a real session,
that is the answer - the row is wrong, and the fix belongs in the table, not
in a comment.

Two limits worth stating plainly, because a player will otherwise read them as
bugs:

  1. A jam started from a client cannot be stopped from that client. The
     multiplayer mod forwards a jam order but has no "stop jamming" order, so
     the host's jam task runs until it ends by itself. The menu says so when
     you stop it.
  2. Damage, hits and sensor outcomes are the host's. Nothing here claims a
     different result from the one the authoritative machine reached.

2F. POINTING A JAMMED MISSILE AT THE SEA  -  PART OF DEFENSIVE ECM
------------------------------------------------------------------

This is what finishes a defensive jam. It is also the only place in the mod
that touches a weapon rather than a ship  -  and it never destroys one.

A sea-skimmer whose seeker loses lock loses its height reference, stops
correcting, and the sea wins. So once an armed ship's jammer has a missile
inside EcmDiveNm (10 nm by default):

  1. **The guidance link is broken *the way the game does it*** -
     ConnectionLost set true and _lostGuidanceTime stamped with the mission
     clock. The missile then coasts on its last track, which is a state its
     own code already understands for a jammed missile.
  2. It is aimed at the water using the flight model's own numbers - its
     orientation is assigned every frame (pitch towards the sea, heading held)
     and its _velocityVecInUnity is written to match, so the physics step
     integrates a real descent rather than a dragged model.
  3. The nose stops at 90 degrees, and gets there faster the higher the weapon
     is: 6 deg/s below 1,000 m, 18 deg/s to 5,000 m, 30 deg/s above. Past
     vertical it would be pointing at the sky.
  4. The descent is metred. A pitch is worked out from the height and the
     weapon's own speed, and the height is walked down a straight line over
     2.5 to 20 s. A sea-skimmer at 15 m noses over by about a degree and takes
     a couple of seconds; one at 5,000 m pitches much harder.
  5. The game removes it. Missile.OnUpdateEveryFrame carries this game's own
     water-dip destruction path; at the waterline the mod stops writing and
     that path does the rest.

10 nm, not 2, and that is about the descent. A sea-skimmer closing at 600
knots covers two miles in twelve seconds. From ten miles it has about a
minute.

What 0.20.0 did wrong, and why this version exists. "Breaking the lock" was
implemented by finding any member whose name mentioned a target or a seeker
and setting it to null - on this type, _seeker and CurrentTarget.
Missile.OnFixedUpdate carries motion integration, guidance, seeker, fuse and
state machine and dereferences both, so the game threw a
NullReferenceException every physics tick: the "Repeated Exceptions" warning,
a missile that stopped in mid-air, and the mod still rotating its transform,
so it span on the spot. This build never writes null to a reference. The
report says so, and lists every member it did write.

Nothing here calls Detonate, Explode, SelfDestruct or Destroy either. Two
earlier builds did, and the player saw both: a warhead going off two miles off
the bow once per tick, and then - once that was narrowed to a plain Destroy -
a NullReferenceException inside GameMain.FixedUpdate with the missile left
sitting on the water, because the game was still walking an object that had
been deleted from under it.

  Task force switch

        either: Defensive ECM: task force off - click to arm N ship(s) arms

  Not covered

Making it less powerful

Worked perfectly, and too well: a jammer that kills every missile in a salvo
makes the enemy's anti-ship missiles pointless. Four settings dial it back,
and none of them is an artificial difficulty switch - each one is a thing that
actually limits a ship's ability to do this.

  Features/EcmDiveChannels
      Default: 3
      What it does: How many missiles one ship can hold down at once (1-99).
        At three, a two-missile shot is stopped and a four-missile salvo is
        not
      The real-world reason: Ships defend on a handful of guidance channels
        - illuminators and fire-control loops - not on unlimited attention

  Features/EcmDiveIntervalSeconds
      Default: 2
      What it does: Seconds between one missile starting its descent and the
        next being allowed to
      The real-world reason: The crew has to see how the first one went
        before the next solution settles

  Features/EcmDiveReactionSeconds
      Default: 1
      What it does: Seconds between a missile crossing EcmDiveNm and its
        dive starting. The jammer is on it immediately; the descent waits
      The real-world reason: A contact has to be seen, designated, and the
        fire-control solution allowed to settle

  Features/EcmDiveRadarSeekersOnly
      Default: true
      What it does: Only radar seekers can be decoyed. Infrared, imaging,
        optical and anti-radiation missiles are left alone
      The real-world reason: RF jamming cannot blind a heat seeker, and an
        anti-radiation missile is homing on the jammer itself

BepInEx\config\io.github.bomberdeer22.seapoweradvanced.cfg. The player picked

2G. THE FORCE DATALINK  -  SENSORS AND EMCON
--------------------------------------------

The problem. A co-op mission with a side per player - Blue for the host, Cyan
for the guest, the two marked friendly, both hostile to Red - has two task
forces. Every contact picture in this game belongs to one task force, and each
machine detects with its own sensors and writes what it found to its own
force's table. Nothing joins the two, so one player holds a track the other
has never been given: "I could see it and he could not." That is not a bug in
the mission or in the sensors; it is two pictures that were never introduced
to each other.

What the switch does. Every few seconds - three by default,
CoopDatalinkSeconds - each contact this force holds is handed to the other
force through the game's own intel-sharing call - Utils.RevealContactToObject,
the same route a reconnaissance report or a radio link uses. The game builds
the track; the mod supplies only which detector carries it and which contact
it is about.

  Datalink: on, sharing N track(s) - click to stop sharing
      What it does: The switch. Off, and nothing more is handed over

  Datalink: resynchronise both pictures
      What it does: A sweep here, and the multiplayer mod's own contact
        sweeps asked for again

  Datalink: what either side can see
      What it does: Writes datalink.txt

  Reads
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: This force's
        plotting table and spotted list (ContactPicture.Hostiles), every force
        on the machine and its own table, the multiplayer mod's co-op flag and
        its CfgPvP / CfgContactSync switches

  Writes
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: Nothing on a
        ship and nothing on a weapon: one call per track, to the game's own
        sharing routine. No radar is switched, no member is set, nothing is
        created or destroyed

  Passing on
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: Position
        only. The classification argument is 0, which attaches neither a side
        nor a class, so the far force gets a bearing and a position - never an
        identity

  Refused for
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: The game's
        neutral force; the game's enemy force; any force with a unit in our
        own picture as a contact; a force whose plotting table cannot be read;
        a force that has already failed three verification sweeps

  Verified
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: After every
        sweep the receiving force's table is read back and counted. Success is
        the track appeared in their picture, not the call returned

  Report
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: datalink.txt
        - session and role, the multiplayer mod's switches, every force with
        its tracks, how many of our tracks are detected here rather than
        received, and the per-force result of the last sweep

  Honest limit
      A session the multiplayer mod considers co-op - its own
        CoopSessionActive, which is not PvP and connected. A PvP session keeps
        the pictures apart on purpose and this will not touch it: This runs on
        the machine that calls it. What the other player's screen shows is
        decided on their machine by their own detection and by the multiplayer
        mod's contact sync, which is the only thing that carries a contact
        between computers. If that mod has decided a two-side mission is PvP,
        its sharing is off and datalink.txt says so - including which switch
        to change. The mod cannot set that switch for it

Why not simply share more. Two reasons, and both are the game's rather than
the mod's. Identity is not ours to give: a datalink track in the real world
carries a position and a track number, and a force that has not identified a
contact should not learn its class from a friend's radio. And a force we are
plotting as a contact is a force we are already treating as hostile, so it is
exactly the force that must not be handed our picture.

If the two screens still differ, in this order: open datalink.txt and read the
Session block - its co-op flag is the answer more often than not; then try
Datalink: resynchronise both pictures; then check that both players have this
build, because a picture handed over by one build and read by another is not a
thing the game can do.

2H. THE LASER RANGEFINDER  -  SENSORS AND EMCON
-----------------------------------------------

The problem. A warship's optronic director gives a watch team a glass on a
bearing and a range on it. Sea Power has no such thing: the sensor families a
hull's parameter block lists are radar, sonar, ESM/RWR and ECM, so a ship with
every radar silent is blind beyond what its ESM hears - however many optronic
masts the hull actually carries data for.

What it does. A hull whose own sensor list holds an optical, infrared or laser
director can be ordered to look with it. Every few seconds each contact the
force already holds that is inside the range and inside the arc is put on the
ship's picture through the game's own reveal call
(Utils.RevealContactToObject, the route a reconnaissance report uses).
Position only.

  Reads
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: The hull's own sensor list for the fit, the player's
        contact picture (ContactPicture.Hostiles), the hull's own plotting
        table, range and bearing to each contact

  Writes
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: One call per sighting, to the game's own reveal
        routine. No radar is switched on or off, no member of the ship is set,
        nothing is created or destroyed - so it works identically at EMCON
        silent

  Passing on
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: Position only. The classification argument is 0: no
        side, no class, no identification

  Limited by
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: LidarRangeNm (12 nm), LidarArcDegrees (90, a quarter of
        the horizon either side of the bow), one beam per hull, LidarSeconds
        (4) between looks

  Never
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: Looks for a contact the force's picture does not
        already hold. A unit that is not in the picture is not a candidate -
        that rule is the difference between a sight and a wallhack, and it is
        also how the real thing is used: a rangefinder is pointed on a bearing
        somebody else's picture gave you

  Refused for
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: A submarine (no line of sight at depth); a hull with no
        director in its own sensor list; a hull whose fit could not be read; a
        contact the force's own sensors already hold - that fix is better than
        anything a reveal can write

  Verified
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: After every look the hull's table is read again and the
        contact has to be in it. Success is the track appeared, not the call
        returned

  Report
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: lidar.txt - the settings and the order in force, the
        last sweep's verdict per ship, and every hull class with the sensor
        families its own parameter block holds

  Honest limit
      A director in the hull's own sensor list - Optronic, Optical, Laser,
        Rangefinder, Designator, IRST, FLIR, Television, Sight and their
        relations. Read by class name from the installed game, positive
        evidence only: This game has no laser sensor, so this is a mod-side
        aid built on the game's own reveal call, not a sensor in the
        simulation. Most base-game hulls will be refused because their sensor
        list holds no optical director - that is the feature refusing rather
        than guessing, and the report shows the list it read

If a hull that should have a director is refused, send lidar.txt: it prints
each hull class and the sensor families its own parameter block holds. A
director filed under a name the mod does not recognise shows up there by name
and can be added.

12. BATTLE STATIONS FATIGUE  -  READINESS
-----------------------------------------

Fatigue accumulates while the ship is at action stations: 15 minutes of
general quarters makes a crew fully tired, and a tired crew gives back up to
25% of the reload saving. Standing down recovers more slowly than tiring, so
there is a real cost to leaving the fleet closed up all mission.

  Shown
      The same _remainingReloadTime shave, with the penalty subtracted: The
        current state and fatigue percentage in the Readiness submenu

  Honest limit
      The same _remainingReloadTime shave, with the penalty subtracted: Crew
        fatigue is entirely the mod's model. The game has crew skill, not crew
        tiredness.

WHAT TO SEND BACK IF SOMETHING MISBEHAVES
-----------------------------------------

seapoweradvanced.log (mod folder), capabilities.txt and ecm-report.txt (same
folder), plus ecm-dive.txt if a missile was not put down when it should have
been. The log names every feature and its result per ship, so a single failed
action is easy to find; the two report files say what the game actually
exposes.

In a multiplayer session, add multiplayer.txt: it names the multiplayer mod's
version, which side of the session this machine is on, and every rule that
followed from it. If the two players are seeing different contacts, add
datalink.txt as well - it is written from the menu (Datalink: what either side
can see) and says whether the session is being treated as co-op, which is the
answer more often than not.
